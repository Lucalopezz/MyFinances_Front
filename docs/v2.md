# V2 do Front-end

Lista de melhorias planejadas para a próxima versão do front-end. Este documento adapta o planejamento da API para as telas, fluxos, estados e integrações do front.

---
## Dashboard

- Ajustar a dashboard para deixar claro que os dados exibidos são mensais.
- Exibir o resumo financeiro do mês de forma semelhante ao resumo da tela de transações.
- Revisar labels, cards e gráficos para reforçar o período analisado.
- Garantir que filtros de data e cards de resumo estejam alinhados com o mês selecionado.
- Ajustar os services e componentes para consumir os períodos retornados pela API sem recalcular regras de negócio no client.

## Despesas Fixas

- Ao marcar uma despesa fixa como paga, exibir o resultado da criação automática de uma transação de despesa feita pela API.
- Refletir no dashboard e nas listas que a transação criada descontou o valor da despesa fixa do saldo do usuário.
- Permitir exibir ou selecionar uma categoria padrão para a transação gerada, como `UTILITIES`, `HOUSING`, `SUBSCRIPTIONS` ou outra categoria escolhida pelo usuário, conforme contrato da API.
- Tratar estado de erro quando a API impedir transações duplicadas para a mesma despesa fixa no mesmo ciclo.
- Exibir, quando disponível, o vínculo entre `FixedExpense` e `Transaction` para rastrear qual transação foi gerada pelo pagamento.
- Revalidar `fixed-expenses`, `transactions`, `dashboard` e comparativos após a marcação de pagamento.

## Comparativo Financeiro

- Adicionar a taxa de economia ao comparativo, consumindo o valor da API ou calculando apenas quando o contrato exigir:

```ts
taxaEconomia = (saldo / receitas) * 100
```

- Exibir melhor mês e pior mês do período analisado.

Exemplo:

```plaintext
Melhor mês: Maio/2026 - R$ 1.000 positivo
Pior mês: Abril/2026 - R$ 300 negativo
```

- Adicionar comparativo com o semestre anterior.
- Exibir gastos por categoria no semestre.
- Considerar indicadores adicionais:
  - total de receitas no semestre;
  - total de despesas no semestre;
  - saldo acumulado;
  - categoria com maior gasto;
  - variação percentual entre semestres.
- Criar estados de loading, vazio e erro para cada bloco do comparativo.
- Garantir formatação consistente de moeda, percentual e mês/ano.

- TODO: Avaliar filtro de mês analisado na dashboard como preferência/configuração futura, sem expor campo de digitação direta na primeira versão.

## Segurança e Privacidade

- Ajustar o front para trabalhar com dados sensíveis de transações criptografados pela API.
- Avaliar impacto visual e funcional nos campos `value`, `description`, `category`, `date` e outros dados financeiros.
- Evitar logs client-side com payloads financeiros ou tokens.
- Garantir que dashboard, comparativos, wishlist e relatórios continuem funcionando quando a API retornar dados já descriptografados para usuários autorizados.
- Avaliar impacto em filtros, ordenação, agrupamentos por data e cálculos financeiros quando parte dos dados não estiver disponível no client.
- Adicionar testes para criação, leitura, atualização e remoção de transações considerando contratos com dados sensíveis.
- Documentar no front quais dados podem ser renderizados, armazenados em cache ou mantidos somente em memória.

- Consumir o relacionamento explícito entre despesa fixa paga e transação gerada quando estiver disponível.

- Integrar novos endpoints para comparativos semestrais e gastos por categoria.
- Preparar o front para trabalhar com campos de transação criptografados sem expor dados sensíveis em logs, toasts ou estados persistidos.

- Adicionar testes de integração ou mocks para:

  - taxa de economia;
  - melhor e pior mês;

## Refatoração de Busca e Cache

- Manter Server Components para buscar os dados iniciais das páginas privadas, preservando SSR, cookie HTTP-only e renderização inicial no servidor.
- Usar React Query nas partes interativas: listas, diálogos, mutations e invalidação após criar, editar, excluir ou marcar pagamento.
- Reaproveitar Server Actions/funções server-side como transporte das queries e mutations para não expor o JWT no browser.
- Centralizar query keys e hooks por domínio, sincronizando cache client-side com `revalidateTag`/`revalidatePath` no servidor.
- Aplicar a migração de forma incremental em transações, wishlist e despesas fixas, sem mudar regra de negócio.
